Lets a course override which proctoring detectors run for a specific module or item, instead of every item in a course being forced to use the same course-wide detector list.

Not its own `modules/` folder — it's a thin layer of fields, validators, and a resolver function threaded through the **Courses**, **Settings**, and **Anomalies** modules. It reuses the detector shape the course level already had; nothing new was invented.

### 🎯 Key Features

- **Per-detector control**, not just an on/off switch — a module or item can enable *only* Blur Detection while the course otherwise has Camera+Mic and Face Recognition on.
- **Three-tier precedence**: item overrides module overrides the course-wide ("universal") setting.
- **`null`/absent means inherit** — a module or item with no override falls through to the next tier untouched. Every module/item that existed before this feature shipped has no override, so the fallback path is exactly the old behavior.
- **One shared shape** (`IDetectorSettings[]`) at all three tiers — the same 8-entry array the course-level `ProctoringModal` already validated, stored, and rendered before this feature existed.

### 🧑‍🏫 How to Use

**Course-wide (universal) setting** — unchanged by this feature. In the course editor's Proctoring settings, pick which of the 8 detectors run for every item in the course. Anything not overridden below inherits this.

**Module-level override** — in the course editor, select a module from the left-hand tree. Its detail panel has a **Proctoring** card:

1. Flip **"Custom detectors for items in this module"** on. This starts the override from a clean *all-unchecked* state — it does **not** pre-fill the course's current detectors, so check whichever ones you actually want before saving.
2. Check/uncheck individual detectors (Camera + Microphone, Blur Detection, Face Count Detection, Hand Gesture Detection, Voice Detection, Virtual Background Detection, Right Click Disabled, Face Recognition). Each checkbox saves itself immediately — no separate "Save" button, and rapid successive clicks are all captured correctly (no need to click-and-wait between them).
3. Every item in this module now uses this detector list instead of the course-wide one, unless an individual item below has its own override (see below).
4. Flip the switch back off to remove the override entirely — the module goes back to inheriting the course-wide setting. Leaving the switch **on** with every box **unchecked** is a different, deliberate state: proctoring is explicitly *off* for this module, even if the course has it on.

**Item-level override** — select an item instead of a module; the same Proctoring card appears on its panel, with identical behavior. An item's own override always wins over its module's override and the course-wide setting — use this to require proctoring on one high-stakes item in an otherwise-unproctored module, or to exempt one item from an otherwise-proctored module.

**Effective precedence when both a module and item override exist**: item wins, full stop — the module override only matters for items in that module that don't have their own override.

### 🧬 Data Model & Precedence

8 detectors, defined once in `ProctoringComponent` (`shared/database/interfaces/ISettingRepository.ts`):

`cameraMic`, `blurDetection`, `faceCountDetection`, `handGestureDetection`, `voiceDetection`, `virtualBackgroundDetection`, `rightClickDisabled`, `faceRecognition`.

An override is `IDetectorSettings[]` — one `{ detectorName, settings: { enabled } }` entry per detector, **all 8 required** (`containsAllDetectorsConstraint` rejects a partial list) — or `null` to clear the override and inherit again.

All resolution goes through one function, `resolveProctoringDetectors` (`shared/interfaces/models.ts`):

```ts
resolveProctoringDetectors(item, module, courseSettings)
  → item?.proctoringDetectors != null   ? item.proctoringDetectors
  → module?.proctoringDetectors != null ? module.proctoringDetectors
  → courseSettings?.settings?.proctors?.detectors ?? []
```

The check is `!= null` (catches both `undefined` and `null`) — MongoDB serializes a field that was never set on insert back as `null`, not `undefined`, so checking only `undefined` would misread every untouched module/item as "explicitly overridden to nothing enabled." Two small helpers sit next to it and should be used instead of reading the array directly: `isProctoringActive(detectors)` (is *anything* on) and `isDetectorEnabled(detectors, name)` (is *this one* on).

### 🔁 Workflow

1. **Teacher edits an override** — `teacher-course-page.tsx` renders a "Custom detectors" `Switch` plus an 8-checkbox `<DetectorChecklist>` for the selected module or item. Turning the switch off sends `detectors: null` (clear override → inherit); turning it on seeds `allDetectorsOff()` so the teacher starts from a clean slate, not the currently-inherited values.
2. **Save** — `useUpdateItemProctoring`/`useUpdateModuleProctoring` PUT the array to `ItemController`/`ModuleController`, which persist it via `ItemService`/`ModuleService` and log the before/after through `AuditTrailsHandler`.
3. **Student reads an item** — `ItemService.readItem`'s student branch calls `resolveProctoringDetectors` and returns the *resolved* list as `item.proctoringDetectors`, not the raw stored override. `student/course-page.tsx` swaps that into the `settings` object it passes to `<FloatingVideo>`.
4. **Detectors arm** — `floating-video.tsx`'s `isComponentEnabled(name)` does a generic `detectors.find(d => d.detectorName === name)` lookup against whatever list it's given, so it needed no changes to respect a per-item resolution — it was already generic over the detector list.
5. **Anomaly recording is gated the same way** — `AnomalyController`'s `/record/image` handler resolves the item's effective `FACERECOGNITION` state via the same `resolveProctoringDetectors`/`isDetectorEnabled` pair before accepting a face-recognition anomaly, instead of checking only the course-wide setting (which used to ignore item/module overrides entirely — a real gap this feature closed as a side effect).

### 🛠 Concurrency handling (teacher checklist)

Clicking several detector checkboxes in quick succession went through three iterations before it was reliable — worth knowing before touching `saveItemDetectors`/`saveModuleDetectors` in `teacher-course-page.tsx` again:

1. **Ref-based re-entrancy guard** — a plain `useRef` checked synchronously before any `await`, closing a lost-update race where a second click's `onChange` read a stale pre-toggle `value` because React hadn't yet committed the first click's state update.
2. **Drain-loop queue** — the guard alone silently *dropped* any click landing while a save was in flight. A single-slot `pending` ref now records the latest queued value; the in-flight save drains it in a loop after each request settles, so a burst of rapid clicks all eventually land instead of only the first one surviving.
3. **Don't disable the controls while saving** — `disabled={isBusy}` (isBusy tracked the mutation's `isPending`) still discarded clicks that landed during the brief window between drain-loop iterations, because a disabled Radix checkbox/switch never fires `onChange` at all — the click never reaches the ref-guard or the queue. The controls are no longer disabled during a save; the ref-guard + queue from steps 1–2 already handle concurrent input safely, so disabling them was actively counter-productive. The spinner next to the switch is a passive indicator only.

### ⚠️ Known limitations

- **Weak auth on the underlying proctoring endpoints** (course/user level) is pre-existing and out of scope for this feature — not hardened here.
- **`handGestureDetection` and `focus` are hardcoded off** in `floating-video.tsx` regardless of what any tier's settings say (`isHandGestureDetectionEnabled = false`, `isFocusEnabled = false`) — a module/item override can still *claim* hand-gesture detection is on, it just won't arm anything, matching pre-existing course-level behavior.
- **`EditProctoringModal.tsx` hardcodes its Blur Detection checkbox as `disabled`** at the course level only; the module/item `<DetectorChecklist>` does not carry that restriction.
